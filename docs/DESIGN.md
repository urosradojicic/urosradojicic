# Animated profile README — design

An animated GitHub profile built from four self-contained SVGs and a daily
GitHub Actions cron. No profile-stats services, no token, no JavaScript.

The constraint everything follows from: GitHub strips `<script>` from READMEs
and sanitises nearly all inline CSS, but it does render SVGs embedded through
`<img>` and runs their CSS animations. So all motion lives inside the SVGs and
the README only places them.

## Components

| File | Size | Generated by | Refreshed |
|---|---|---|---|
| `ascii-portrait.svg` | 618×567 | `prep_photo.py` → `make_portrait.py` | when the photo changes |
| `info-card.svg` | 490×337 | `make_info_card.py` | when `data/profile.json` changes |
| `shipped.svg` | 860×324 | `make_shipped.py` | when `data/profile.json` changes |
| `contrib-heatmap.svg` | 860×226 | `fetch_contributions.py` → `render_heatmap.py` | daily, by Actions |

All content lives in `data/profile.json`. Editing the profile means editing that
file and re-running `build.py` — no Python is touched.

## Decisions

**One theme module.** `theme.py` owns the palette, the terminal chrome, the font
stack and XML escaping. Four images meant to read as one terminal drift apart
the moment one is edited alone.

**Opaque backgrounds, not transparent.** A README renders on the *visitor's*
theme. Light-grey glyphs on transparent vanish in light mode.
`prefers-color-scheme` inside the SVG does not fix this — loaded through `<img>`
it resolves against the browser/OS preference, not GitHub's theme toggle, so a
visitor on OS-light with GitHub-dark gets the wrong variant. Painting the
background makes all four pixel-identical for everyone.

**Split requirements.** `requirements-daily.txt` is two packages. The portrait
toolchain (`pillow`, `numpy`, `rembg`) is local-only — installing ~250 MB of
ONNX runtime every morning to scrape one HTML table would be absurd.

**Two `<img>` tags, not a `<table>`.** GitHub's markdown CSS puts a border on
every `td`, and a fixed-width table overflows on a phone. Two adjacent images
are border-free and wrap to a stack when the container is narrow. The newline
between them collapses to one space (~4.4px) which serves as the gutter.

**Background removal is required, not optional.** The ASCII ramp maps bright to
blank, so a *white* backdrop disappears and only the subject prints. The source
photo's mid-tone backdrop maps to mid-density glyphs instead, embedding the face
in a rectangle of noise.

## Things that bite

**The contribution endpoint has no counts.** `github.com/users/<login>/contributions`
returns `<td data-date data-level>` cells that are *empty*. The number lives only
in a sibling `<tool-tip for="...">` as English prose — `"No contributions on
July 27th."`, `"17 contributions on April 13th."` A parser that reads only the
cells yields a correctly shaped calendar in which every day is zero, and renders
without erroring. `data-level` is not a substitute: it is a 0–4 bucket relative
to the account's own busiest day.

**Private commits are excluded at the source** unless *Include private
contributions on my profile* is enabled. No scraping recovers them.

**`transform-box: fill-box` is load-bearing.** Without it a percentage
`transform-origin` on an SVG shape resolves against the SVG root's origin, so
`scale` throws the cell across the canvas instead of growing it in place.

**Four tenths of a pixel wraps a row.** `368 + 4.4 + 488 = 860.4` in an 860
container silently dropped the card onto its own line. Both images still
rendered; the layout was just wrong. Widths are now 365 + 487, leaving ~2.6px
slack. Verified by measuring `getBoundingClientRect()`, not by arithmetic.

**Animations do not advance in a non-compositing document.** When
`document.visibilityState === "hidden"` — a hidden pane, a headless run — CSS
animations stay frozen at t=0, where `.wipe` is clipped to zero width and
`.fade`/`.pop` are at opacity 0. Everything looks blank and nothing is wrong.
`audit-layout.browser.js` forces each animation to finish through the Web
Animations API instead of waiting on wall-clock time.

**Canvas rasterisation shows the same frozen frame,** so sampling pixels from
`drawImage` cannot verify content. Inlining the SVG and reading computed styles
can.

**Chrome reports the finished clip as `inset(0px 0% 0px 0px)`** — it keeps the
unit it animated from. Matching against `inset(0px)` produces a false failure.

## Verification

`verify.py` — static, no browser. Parses each SVG: geometry inside the canvas,
animation declarations present, portrait rows equal length with `textLength`
pinned, and the *rendered* layout computed from the `width=` attributes in
`README.md` rather than the SVGs' natural sizes.

`audit-layout.browser.js` — in a browser. Side-by-side row, gutter, slack,
height match, phone overflow, and that every animated element reaches a visible
end state.

## Cost

Zero. Actions minutes are free and unmetered on public repositories, every
package is free, and there is no third-party service in the render path.
